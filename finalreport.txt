Project Specification & Management

2.1 The Project Specification (The AI's Blueprint + Link): 
Our project's master instruction set is governed by `backend-spec-doc.md` and `AGENTS.md`. This specification acts as an "Agent-Ready" blueprint that strictly bounds AI behavior. It defines the headless middleware architecture, data schemas, API routes, and explicitly enforces constraints such as a "Zero-UI Policy", strict Zod environment validation, UUIDv7 standards for primary keys, and mandatory compliance with RFC 9457 (Problem Details for HTTP APIs) for all error handling.

2.2 Maintaining the "Single Source of Truth": 
To keep the AI agents aligned, we utilized `AGENTS.md` as a living roadmap and checklist. Whenever architectural pivots occurred—such as migrating from `node-cache` to `redis` or adding the new Daily Games Prisma schemas—both `AGENTS.md` and `backend-spec-doc.md` were manually updated. This ensured the AI's context window always reflected the absolute current state of the codebase, preventing hallucinations and preventing agents from referencing deprecated implementation strategies.

2.3 Key Milestones: 
*   **Foundation & Infrastructure:** Completion of the basic Express/TypeScript scaffolding with strict Zod environment validation and global RFC 9457 error handling.
*   **Core MVP (The Proxy):** Successful deployment of the WordPress data proxy, which fetches, strips, and paginates raw CMS data into "Lean" articles.
*   **Authentication & User State:** Implementation of WorkOS Magic Auth (passwordless OTP), allowing users to persist Bookmarks and Push Notification preferences in PostgreSQL.
*   **Performance Optimization:** Integration of Redis caching with background cache-warming polling to ensure instantaneous feed delivery.
*   **MVP 2 Expansion:** Deployment of the Daily Games API (challenges, scoring, leaderboards) and full server-side PostHog user analytics integration.

System Architecture & High-Level Design

3.1 System Overview: 
The solution is a headless Node.js/Express middleware service acting as a secure gateway between a mobile client and external data sources (WordPress, WorkOS). It exposes a versioned REST API (`/v1`). Key endpoints include `GET /v1/feed` (returning paginated, stripped CMS content), `POST /v1/auth/request-otp` (handling passwordless login via WorkOS), and `GET /v1/games/:gameId/leaderboard` (delivering daily challenge results).

3.2 Architecture Diagrams: 
*   **Data Flow:** Mobile Client requests hit the Express API Gateway. For news content, the server checks the Redis cache; on a cache miss, it queries the external WordPress API, strips out heavy HTML metadata, caches the payload, and returns it to the client. User-specific actions (e.g., Bookmarks, Games) read/write directly to the PostgreSQL database via Prisma.
*   **Database Schema:** At the core is the `User` entity (UUIDv7). Users have one-to-many relationships with `Session` (for token revocation), `Bookmark`, `PushToken` (for Expo notifications), and `UserGameStats`. A `Game` contains daily `Challenge` entities, and a `GameResult` securely links a `User`'s score and duration to a specific `Challenge`.

3.3 Key Architectural Decisions and Trade-offs: 
*   **Data Transformation Proxying:** Instead of the mobile client querying the CMS directly, the Node.js middleware intercepts the payload and maps deeply nested CMS data into a "Lean Article" interface. This vastly reduces mobile bandwidth consumption and parse times.
*   **Redis over In-Memory Caching:** We pivoted from `node-cache` to Redis. While `node-cache` was simpler, Redis allows the Node.js server to scale horizontally across multiple instances without cache fragmentation or redundant CMS querying.
*   **Stateful JWTs:** We traded the pure statelessness of JWTs for a stateful `Session` table in PostgreSQL. This allows us to instantly revoke compromised devices during a `/v1/auth/logout` event while still utilizing the WorkOS passwordless flow.




































Implementation & AI Orchestration

4.1 Technologies Used: 
*   **Node.js & Express (TypeScript):** Forms the core API gateway and runtime environment.
*   **Prisma & PostgreSQL:** The ORM and primary relational database storing user profiles, sessions, bookmarks, and game statistics.
*   **Redis:** The caching layer that intercepts WordPress requests to ensure high-speed feed delivery.
*   **WorkOS:** Third-party service integrated to handle the delivery and verification of email OTPs for passwordless authentication.
*   **Zod:** Used heavily for strict runtime validation of both incoming API request bodies and environment variables at startup.
*   **Expo Server SDK:** Handles formatting and routing push notification payloads to APNs and FCM without managing platform-specific certificates on our backend.
*   **posthog-node:** Captures server-side user analytics securely, tracking OTP funnels and game interactions.

4.2 AI Build Strategy: 
The AI orchestration was heavily constrained by a set of system personas defined in `AGENTS.md`. The core mechanism was "The Golden Rule: Approval First," which strictly forbade the AI from modifying code without first presenting a Code Plan. We used explicit prompt logic restrictions such as "Zero-UI Policy" (preventing the AI from generating React or HTML since this is a headless API), "Schema First" (forcing database design discussions prior to logic implementation), and "Import Discipline" (forbidding the assumption of global libraries).
